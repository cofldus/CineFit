# 검증 레지스터 — 확정 사실 vs 검증 대기 사실

- 목적: 설계 문서(01~12)에 인용된 핵심 사실 중 **구현 전 근거 URL·확인일 연결이 필요한 항목**을 관리한다.
- 운영 규칙: 항목별로 `상태`가 `검증 대기`인 동안은 해당 사실을 근거로 한 기능을 "확인 필요" 라벨 없이 출시하지 않는다.
- 상태 값: `확정(URL·확인일 연결됨)` / `실측 확인` / `검증 대기(URL 미연결)` / `재검증 필요(정보 노후)`

## 1. 극장 3사 robots.txt — 자동 수집 제한

| 대상 | 확인 결과 | 근거 URL | 확인일 | 상태 |
|---|---|---|---|---|
| CGV | 일반 UA는 `Allow: /`이나, ClaudeBot·GPTBot·CCBot·Bytespider 등 AI 봇 다수 `Disallow: /` 명시 + Content-Signal `ai-train=no, use=reference` | https://www.cgv.co.kr/robots.txt | 2026-07-27 | 실측 확인 |
| 메가박스 | robots.txt 원격 조회 자체가 실패(차단 추정) — 문서 01 §5의 "접근 차단" 기술과 일치. 브라우저 수동 접근으로 교차 확인 권장 | https://www.megabox.co.kr/robots.txt | 2026-07-27 | 실측 확인(조회 불가) |
| 롯데시네마 | `User-agent: *` / `Disallow:` (공란) — 형식상 전체 허용. 단 약관 검토 전 보수적 접근 유지(문서 07 §1) | https://www.lottecinema.co.kr/robots.txt | 2026-07-27 | 실측 확인 |

> 시사점: 문서 01·07의 판단(자동 수집 부적합, 수동 입력+딥링크)은 유효. robots.txt는 변경될 수 있으므로 분기 1회 재확인.

## 3. 처리 원칙

1. 항목 1·5(상영관 사양)는 DB에 넣을 때 `info_status='user_report'` 이하로 기록하고, 검증 완료 시 observation 승격(문서 06 §1).
2. 항목 2(회생절차)는 `cinema_locations.status='uncertain'` 처리의 근거이므로, 상태 변화(개시/인가/폐지) 시 즉시 반영.
3. 항목 3·4(API 약관)는 **스파이크 단계에서 키 발급 시 약관 원문을 이 문서에 인용**하는 것으로 완료 처리.
