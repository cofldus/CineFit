# 장애 대응 가이드 (초안)

- 기준일: 2026-07-29 (8차 마일스톤)
- **이 문서는 초안이다.** 아직 실제 배포·실사용자가 없어(`docs/ALPHA-PLAN.md`) 실전에서
  검증된 절차가 아니다 — 지금 코드가 실제로 제공하는 대응 수단을 정확히 적은 것이다.
- 1인/소규모 팀 운영을 전제로 한다 — "누가 대응하는가"(온콜 로테이션, 연락 채널)는 실제
  알파 시작 전 사람이 채워야 한다(아래 표시된 자리표시자 참고).

## 감지 수단 (지금 있는 것)

| 수단 | 확인 방법 |
|---|---|
| 헬스 체크 | `GET /api/health` — DB 연결 확인, 인증 불필요(`docs/DEPLOYMENT.md`) |
| 구조화 로그 | Vercel 배포 로그에서 `event` 필드로 검색(`src/lib/logger.ts`, `docs/OPERATIONS.md`) |
| 알파 운영 대시보드 | `/admin/alpha-ops` — 세션·동의·사용 퍼널 이상 징후(급락 등) |
| 감사 로그 | `audit_logs` 테이블 — 관리자 조작·기능 플래그 변경·삭제 요청 처리 이력 |
| 예매 링크 상태 | `/admin/booking-links` — 예매 URL 응답 이상 |

지금은 알림(alerting)이 없다 — 누군가 위 화면을 직접 열어봐야 안다. Uptime 모니터링
서비스(예: 외부 핑 서비스가 `/api/health`를 주기적으로 호출)를 붙이는 것은 실제 배포 시
사람이 결정할 일이다.

## 즉시 쓸 수 있는 완화 수단

- **기능 플래그 끄기** — `/admin/feature-flags`에서 즉시 반영(배포 불필요). 문제가 특정
  기능(예: `private_alpha_gate`)에 국한되면 배포 롤백보다 빠르다.
- **회차 비활성화** — `/admin/showtimes`에서 개별 회차를 `disabled`로(삭제 아님, 이력 남음) —
  잘못된 정보가 노출 중이면 우선 이걸로 막는다.
- **배포 롤백** — Vercel 대시보드 → Deployments → 이전 배포로 즉시 전환.
- **개인정보 삭제 요청 처리 중단** — 오남용이 의심되면 `/admin/privacy-requests`에서 개별
  요청을 반려하고, 필요하면 그 세션의 `alpha_consents`를 관리자가 직접 확인한다(전용 UI는
  없다 — DB 직접 조회 필요, 알려진 한계).

## 시나리오별 절차

### 1. 사이트 전체 오류/응답 없음
1. `/api/health` 호출 — DB 문제인지(503) 앱 자체 문제인지(타임아웃/5xx) 구분.
2. Vercel 배포 로그에서 최근 배포 이후 발생했는지 확인 → 그렇다면 즉시 이전 배포로 롤백.
3. DB 문제면 Supabase 대시보드에서 인스턴스 상태 확인(일시정지·장애 등).
4. `proxy.ts`의 비공개 알파 게이트는 DB 조회 실패 시 **자동으로 열린다**(fail-open,
   `docs/PRIVATE-ALPHA.md`) — 게이트 자체가 다운 원인일 가능성은 낮다.

### 2. 잘못된 상영 정보(회차·가격 등) 노출
1. `/admin/showtimes`에서 해당 회차를 즉시 `disabled` 처리.
2. 근본 원인(등록 실수·예매 페이지 변경) 확인 후 올바른 값으로 새 회차 등록(수정이 아니라
   이력 추적을 위해 `docs/DEVELOPMENT.md` 운영 절차를 따른다).

### 3. 개인정보 관련 사고(의심되는 유출·오남용)
1. 영향 범위 파악 — 어떤 테이블·세션·이메일이 관련됐는지(`docs/DATA-DELETION.md`의 테이블
   목록 참고).
2. 관련 기능을 즉시 플래그로 끄거나(가능한 경우) 배포 롤백.
3. 영향받은 사용자가 식별 가능하면(제보에 남긴 이메일 등) 직접 안내 — 이 문서는 통지 문구
   템플릿을 아직 제공하지 않는다(실제 알파 시작 전 준비 필요, 알려진 gap).
4. `audit_logs`에서 사고 전후 관리자 조작 이력을 확인해 원인을 재구성한다.
5. 사고 요약을 이 문서 하단 "사고 이력"에 기록한다(날짜·원인·조치·재발 방지책).

### 4. 남용(스팸 제보, 반복적인 삭제 요청 등)
- 제보 제출은 세션 해시 기준 시간당 5건(`src/data/reportService.ts`), 삭제 요청은 시간당
  3건으로 이미 제한돼 있다(`src/data/privacyRequestService.ts`).
- IP 차단·세션 강제 종료 기능은 없다(알려진 한계) — 심하면 해당 기능을 플래그로 끄거나
  Vercel의 방화벽/Rate limiting 기능(플랫폼 자체 제공)을 사람이 직접 설정해야 한다.

### 5. 예매 링크 대량 오류(공식 사이트 구조 변경 등)
1. `/admin/booking-links`에서 `expired`/`not_found`/`blocked` 비율 확인.
2. `npm run maintenance:links`(또는 Vercel Cron이 자동 실행)로 최신 상태 재확인.
3. 실제로 링크가 깨졌으면 해당 회차들을 개별적으로 재등록·비활성화.

## 알려진 한계 (실제 알파 시작 전 보완 후보)

- 알림(alerting) 자동화 없음 — 사람이 대시보드를 직접 봐야 안다.
- 사용자 통지 템플릿 없음(개인정보 사고 시 안내 문구).
- IP/세션 차단 기능 없음(남용이 심할 경우 플랫폼 레벨 대응 필요).
- 온콜 담당자·연락 채널 미정(1인/소규모 팀 — 실제 알파 시작 전 사람이 정할 일).
